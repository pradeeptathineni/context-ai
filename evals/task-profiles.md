## Explicit resolution checks

[Example profiles](../examples/task-profiles) are builder-authored choices under stated project assumptions. They are not outputs from a natural-language classifier or an uncoached consumer evaluation.

| Request and assumptions | Resolved choice | Verification boundary |
| --- | --- | --- |
| Fix a failing integration in a settled service | Direct diagnosis/API guidance; localized debugging route | Red/green contract checks; live producer remains unverified |
| Review a consequential architecture | Direct technical-design/API/review guidance; PACT; architecture route | Trace failure recovery and preserved data; review-only scope |
| Redesign a page in a recurring project with established style | Web design/test stages; lightweight option, selected notice and browser floor | Actual interactions, keyboard, accessibility and visual inspection still needed |
| Implement an API with explicit criteria and settled architecture | Direct service/review guidance; strong-spec coding route | Schema, authorization, failure and persistence checks on isolated data |
| Change existing Terraform | Direct infrastructure/review guidance; Terraform required, AWS optional | Candidate discovery is separate from isolated validation, authorized plan and deployment |
| Research tool adoption | Direct research/prior-art guidance; PACT; policy model fallback | Maintained original evidence and a project decision; no installation or candidate invocation |
| Correct a README command fully covered by project instructions | No added Context reads, discovery or model recommendation | The project's existing documentation check |

`tests/test_task_profiles.py` checks these resolutions and negative controls: changing only task words cannot change selections or cause effects; unknown fields/IDs/options/stages and unsafe paths fail; opposing primary design procedures fail; a review prerequisite can compose with fresh review; fresh selection requires an explicit matching orchestration recommendation. Model checks cover every current literal route, first-match precedence, absent attributes, wildcard policy and fallback.

The stage control requests web testing only: it retains browser verification but omits design procedures and their upstream resources. Explicit task capabilities survive slicing and strengthen optional requirements. Missing required command candidates remain named packet gaps while persistent materialization still refuses them. A hostile project script/configuration is read as data; subprocess tripwires and before/after retained-file bytes establish no project execution or writes. CLI tests reject selections split between profiles and unrelated flags. Safe input parsing retains duplicate-key, alias, object-tag and size boundaries. The offline contract gate also resolves every example.

## Actual use on this change

The implementing agent used [this profile](task-profile-use.yaml) through the actual CLI in the Context checkout for the review/validation stage. The packet resolved eleven direct guidance resources, required PACT, recommended one agent, left the active model unchanged, and reported execution not run with no writes. The agent had explicitly read those resources during repository inspection and reused that available context; their names in the packet alone were not treated as reads.

The agent then reviewed the actual diff against the task and project requirements, preserved the existing materialization/ownership contract, and ran the required repository, contract, lint and whitespace gates. The task profiles provided inspectable advice rather than project commands. Review refined stage slicing, selected-procedure contradictions and installed-skill reachability: the equipping skill's new contract reference is a declared resource prerequisite, while conditional examples remain source-checkout navigation.

Final local results: all 81 unit/contract tests passed, along with `ruby scripts/validate.rb`, `scripts/check_loadouts.py`, Ruff semantic lint, both changed skill validators and `git diff --check`. No browser task or live integration was changed or exercised for this resolver work.

This is actual builder use on software development, not an independent review or proof that the profile caused better decisions. No agents were dispatched, active model controls changed, tools installed, consumer materialization required, or external deployment performed. The existing host supplied interpretation and execution. Local Python and Node runtimes supported the checks; no paid API or live research producer was invoked.
